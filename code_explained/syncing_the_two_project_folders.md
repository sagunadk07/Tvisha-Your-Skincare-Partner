This walks through fixing the "two copies of the project" situation from
scratch, written so you can do every step yourself and understand *why*
each one exists, not just *what* to type.

## Concepts you need before starting

**A git repository ("repo")** is a project folder that has a hidden `.git`
folder inside it. That hidden folder is what actually stores every saved
snapshot ("commit") of your project's history. A folder *without* a `.git`
folder inside it — like your outer folder right now — isn't tracked by git
at all: there's no history, no backup, nothing. If that folder were
accidentally deleted, everything in it would just be gone.

**A remote** is a copy of the repository's history stored somewhere else —
here, on GitHub, at `github.com/sagunadk07/Tvisha-Your-Skincare-Partner`.
Having a remote means even if your laptop died, the pushed history would
still exist on GitHub's servers.

**The three git "zones" you're moving a change through:**
1. **Working directory** — the actual files on disk, as you edit them.
2. **Staged** — files you've marked with `git add` as "yes, include this
   in the next snapshot."
3. **Committed** — `git commit` takes everything staged and permanently
   saves it as a new snapshot in the repo's history, with a message
   describing what changed.

`git push` then sends any new commits from your computer up to the GitHub
remote, so it also has them.

## The plan

The nested folder already has the `.git` connection to GitHub — so instead
of creating a new repo, we're going to **replace the nested folder's files
with the outer folder's (better) files, while keeping the nested folder's
`.git` folder untouched.** That gets the working code onto GitHub without
losing the existing git connection.

### Step 0 — back up first

Before touching anything, copy the entire outer folder
(`C:\Users\sagun\Tvisha Your SkinCare Partner`) somewhere else — an
external drive, a zip file, wherever — and don't touch that copy again.
This costs nothing and means you genuinely cannot lose work no matter what
goes wrong below.

### Step 1 — copy the files across

In File Explorer (easier than doing this part in the terminal): open the
outer folder, select everything **except** these:
- `.venv` (this is a bunch of installed libraries specific to this machine
  — it doesn't belong in git and doesn't need to move)
- `__pycache__` (auto-generated by Python, never needs to be copied or
  tracked)
- `Tvisha-Your-Skincare-Partner` (that's the nested folder itself — don't
  copy it into itself!)
- `.result-section {.css` (the broken stray file — see the note at the
  bottom)

Copy the rest — `main.py`, `auth.py`, `model_inference.py`,
`face_validation.py`, `recommendation_engine.py`, `requirements.txt`,
`users.db`, `templates/`, `static/`, `test-images/`,
`best_skin_model_8class.pth` — and paste them **into**
`C:\Users\sagun\Tvisha Your SkinCare Partner\Tvisha-Your-Skincare-Partner`,
confirming "yes, replace" when it asks about files that already exist
there (like `main.py`).

### Step 2 — decide what git should ignore

Open `Tvisha-Your-Skincare-Partner\.gitignore` in an editor. It's a plain
text file where each line is a filename or folder pattern that git should
never track. Make sure it has these lines (add any that are missing):

```
venv/
__pycache__/
*.pyc
users.db
```

Why `users.db` specifically: it's a real database of whoever signs up on
your site. Committing it to a public GitHub repo would mean anyone could
download it (password hashes and all). Keeping it out of git means each
place the app runs just creates its own fresh, empty `users.db`
automatically the first time it starts (that's what `init_db()` in
`auth.py` does).

### Step 3 — look at what actually changed

Open a terminal **inside** the nested folder
(`Tvisha Your SkinCare Partner\Tvisha-Your-Skincare-Partner`) and run:

```
git status
```

This lists every file git notices is new, modified, or deleted compared
to the last commit. You should see things like `auth.py` (new),
`main.py` (modified), `templates/signup.html` (new), and so on. Read
through the list — it's your chance to sanity-check that what changed
matches what you expect (all the auth stuff appearing, `scanner.html`
getting much bigger, etc).

If you want to see the actual line-by-line changes for a specific file
before committing, run:

```
git diff main.py
```

(press `q` to exit the scrolling view it opens).

### Step 4 — stage and commit

```
git add .
git commit -m "Add login/signup/admin, fix broken scanner page, bring result page up to date"
```

`git add .` stages every changed file in the current folder (the `.` means
"here and everything below"). The commit message should describe *why*
the change happened, in plain words — future-you (or your supervisor
reading the git history) will thank you.

### Step 5 — push to GitHub

```
git push
```

This uploads your new commit to `github.com/sagunadk07/Tvisha-Your-Skincare-Partner`.
Since you're not force-pushing and not rewriting any existing commit, this
is a completely safe, normal operation — it just adds a new snapshot on
top of the existing history.

### Step 6 — get the app running from this folder

The nested folder's `venv` is missing Flask entirely (that's why it
couldn't start when I tested it). Inside that same terminal:

```
venv\Scripts\pip install -r requirements.txt
```

Then start it and click through it in a browser to confirm everything
still works exactly like the outer copy did:

```
venv\Scripts\python main.py --port 5001
```

Visit `http://127.0.0.1:5001` and test: sign up, log in, upload a photo
on the scanner page, check the result page shows the heatmap slider, log
out.

### Step 7 — retire the outer folder

Once you've confirmed the nested folder works and is pushed to GitHub,
the outer folder has served its purpose. You don't have to delete it
immediately — but stop editing it going forward. Doing all future work
only inside the one git-tracked folder is exactly what prevents this
"two diverging copies" problem from happening again.

## Loose end: the stray `.result-section {.css` file

This file's content is real, valid CSS — but it's not currently used by
either copy (outer's `result.html` already has this same CSS written
directly inside a `<style>` tag in the file itself, so this separate file
is a redundant leftover). Before deleting it, you can double-check nothing
references it by searching the project for its would-be filename:

```
grep -r "result-section" static/ templates/
```

If that finds nothing pointing at a separate `result.css` file, it's safe
to delete.

## Optional, later: merging the nicer result.html

The nested folder's `result.html`/`result.js` had a genuinely nicer
version of the result page (shared layout via `base.html`, a print/download
button, better handling when a condition has no recommendation data yet).
After Step 5 above, that improvement gets overwritten by outer's older
version. That's fine to leave for now — it's a polish task, not a bug fix
— but if you want to bring it back later, the way to approach it is: open
both versions side by side, and for each difference decide "does outer's
version already do this a different way, or is this genuinely new?" rather
than copying one file wholesale over the other, since outer's session
handling (showing "log out" vs "log in" in the nav) needs to stay intact.
